# Win32 Window Manager

On Windows, Automat shows the windows of other programs on its boards as App Windows (`src/win32_window_manager.cpp`). An embedded window stays a top-level window of its program. Automat makes its hidden owner window the owner of the embedded window, which cloaks it, draws a captured image of the window on the board, and passes input to the program as posted messages.

## Input queues

Windows attaches the input queues of two threads when a window of one thread becomes the owner of a window of the other thread. Through the hidden owner window, every embedded program would share Automat's input queue. The mouse capture that Qt takes on a press would then receive Automat's real mouse input, so Krita would draw along the movement of the real pointer relative to its cloaked window instead of under the pointer on the board, and it would keep the capture after the release. `SetHiddenOwner` therefore detaches the two queues right after it makes the hidden owner window the owner of an embedded window. Windows attaches them only when the owner is set, so they stay detached. `Uncloak` makes a temporary window of Automat the owner only for the moment of revealing a window, and the queues are not attached after it returns.

The popups of an embedded program, such as its menus, the lists of its combo boxes and the splash screen of Krita, are cloaked through the embedded window of their own thread: `CloakPopup` makes that window the owner of every popup that has no owner. The popup and its owner belong to the same thread, so no input queues are attached. A popup owned by the hidden owner window would attach the thread of the program to Automat's input queue each time the popup appears. A thread that is not the foreground thread loses its active window and its focus when it is attached, and detaching the queues right after does not give them back. Qt closes all popups when the application is deactivated, and after a replacement by `run.py --live` Krita is never the foreground thread, so its menus would close within 50 milliseconds after they open. When Automat reveals an embedded window, it clears the owner of the transient windows that the embedded window owns, which gives the popups back to the program.

With detached queues, a press that Automat posts does not change the foreground window. A program that Automat launched is an exception, because Windows lets a process that the foreground process started activate its windows. Such a program becomes the foreground window when it handles the `WM_ACTIVATE` that Automat posts the first time its window receives the keyboard focus of the board (`SendFocus`), and its dialogs become the foreground window when they open.

## Presses

A program that tracks the pointer with `TrackMouseEvent` is told that the pointer left as soon as it starts tracking, because the real pointer is over Automat's window. Qt starts tracking on every move that enters its window, so every enter is followed by a leave, and the canvas of Krita starts a stroke only on a press that arrives between an enter and a leave. Automat therefore posts a move to the position of each press right before the press (`AppInputAction`). The system posts the leave while Qt handles the move, and the press starts a stroke when it is queued before that leave. This is the usual order, because Automat posts the two messages one right after the other, but nothing guarantees it: Krita can handle the move before Automat posts the press, and then the press arrives after the leave and does not start a stroke. A leave that arrives during a stroke does not end the stroke.

## Picked windows

An App Window that holds no window shows a pick button, the same button that the Window object uses (`PickButton` and `WindowPicker` in `src/library_window.hpp`). The App Window is offered in the menu of the Beta shelf, so it can be created without a Program Launcher. After a press on the button, the next click selects the top-level window under the pointer, and Escape cancels the pick. `AppWindowToy::OnWindowPicked` binds the window on the window manager thread like the window of a launched program. A window that is already bound to an App Window, a window that `CanEmbed` rejects and a window of Automat itself are not bound. After `run.py --live` replaces Automat, the next instance binds a picked window again by the handle that its App Window saved (`RecoverOrphans`).

The pick (`kPickWindow`) is a menu interface and not a command, because a command would be the only command of an App Window: it would appear in the menu of every App Window and could be run without a pointer.

The pick button lies inside the content area, so `AppWindowToy` uses its own shape as the shape of its subtree. For a frame with a title, the union that `Widget::SubtreeShape` computes from the shape of the frame and the shape of the button has a hole where the button is, so a press on the button would reach the board instead.

## Window captures

Automat draws an embedded window and each of its popups from a Windows.Graphics.Capture session (`src/win32_capture.cpp`). A capture lives as long as its window. It ends when its capture item reports `Closed`, which happens after the window is destroyed.

Automat never ends a capture as a reaction to the hiding or the destruction of its window. The capture service deadlocks when `GraphicsCaptureSession.Close` arrives while the service handles the destruction of the captured window: the service stops the session under the session lock and waits for its window-closed callback, and that callback needs the same lock. Hiding and destruction are milliseconds apart (the shadow window of a menu is hidden and then destroyed), so a close that reacts to either event can arrive at that moment. The service reports `Closed` after it has stopped the session itself, so a close after `Closed` has nothing to wait for. The handler of `Closed` only posts the close to the window manager thread.

A hidden popup keeps its capture and its mirror, which is marked invisible and is not drawn. Qt reuses the window of a menu each time the menu opens, so a menu is captured once and appears at once when it opens again. The shadow window of a menu is created for each opening and destroyed when the menu closes, and its capture ends through `Closed`. Each hidden popup keeps one idle frame pool thread.

Automat lets go of a capture when the mirror of a destroyed popup is removed, when an App Window is deleted or bound to another window, and when Automat stops (`~SessionHandle`). It ends the capture at once only while the window is visible. An App Window is also deleted when its window is hidden or destroyed, and Windows hides a window before it destroys it, so a capture of a window that is not visible is left to end through `Closed`. Until then the session keeps itself alive through its `Closed` handler. Its frame textures are released at once, so no Vulkan image outlives the renderer.

A capture item reports `Closed` through the message loop of the thread that created it. An item created on a thread without a message loop never reports it. The window manager thread creates the items and runs a message loop, so its items report `Closed` in both COM apartment types.

An App Window whose toy is ticked without being drawn for half a second stops its session and keeps its item (`PauseCapture`). A toy that is off screen is not ticked, so panning the board away does not stop the session. When the toy is drawn again, a new session starts and asks the window to repaint, because the compositor produces a frame only when the program paints.

## Threads

The window manager runs on its own thread, which runs a dispatcher queue (`Post`). The thread joins the multi-threaded COM apartment and then creates the queue for itself (`DQTYPE_THREAD_CURRENT`), because Windows creates a dedicated dispatcher queue thread only in a single-threaded apartment. On a thread of the multi-threaded apartment a cross-process call blocks without pumping messages, so no window event is handled in the middle of another one, and posted events are handled in the order of arrival.

The WinEvent hook stays on the main thread, because Windows delivers out-of-context events through the message loop of the thread that installed the hook, and its callback only posts each event to the window manager thread. On the main thread, a cross-process call made inside the hook callback runs a modal message loop that delivers further events into the same callback, which started duplicate captures. The pause of an off-screen App Window, the Pop Out and Embed commands and the binding of a picked window post to the window manager thread as well. A move that a program starts by itself is passed to the board, which alone knows whether a press is routed into the window (`input_action`); when it is, the board cancels the move of the program with `WM_CANCELMODE` and moves the App Window instead. `CloseWindowsOf` runs on the thread of the caller, so the window manager thread changes `tracked` only under `tracked_mutex`.

`Start` waits until the window manager thread has created its queue and bound again the windows left behind by an Automat that is gone (`RecoverOrphans`), because `LaunchRestoredWindows` runs right after `Start` and launches the program of every App Window that has no window yet. `Stop` waits until the queue has shut down and joins the thread before it lets go of the remaining captures on the main thread. A capture of a window that is hidden at that moment can no longer report `Closed`, and it lives until Automat exits.
